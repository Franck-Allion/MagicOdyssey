# Effect Resolution and Atomic Transactions

**Normative References:** Decisions Q55, Q60, Q61, Q62, Q63, Q64, Q287, Q288, Q289.

---

## 1. Atomic Transaction Pipeline [Q287]

Every state modification in the combat engine executes as an atomic transaction:

```
+--------------------------------------------------------------+
| 1. PREPARATION                                               |
|    - Instantiate candidate EffectOutcome                     |
|    - Compute proposed changes (mana, HP, positions)          |
+------------------------------+-------------------------------+
                               |
                               v
+--------------------------------------------------------------+
| 2. INVARIANT VALIDATION                                      |
|    - Verify costs, targets, bounds, and rules                |
|    - If invalid: ABORT without state mutation                |
+------------------------------+-------------------------------+
                               |
                               v
+--------------------------------------------------------------+
| 3. COMMIT                                                    |
|    - Mutate CombatState atomically                           |
|    - Increment state revision counter                        |
|    - Check victory and defeat conditions                     |
+------------------------------+-------------------------------+
                               |
                               v
+--------------------------------------------------------------+
| 4. EVENT DISPATCH & STABILIZATION                            |
|    - Enqueue generated events into FIFO                      |
|    - Drain FIFO triggers until stable                        |
+--------------------------------------------------------------+
```

### 1.1 Technical Rollback Safety [Q287]
If an unhandled technical exception occurs during stage 1 or 2:
- The candidate operation is discarded.
- Previously committed state revisions remain completely intact.
- The engine logs a structured diagnostic report with the current state revision and RNG seed.

## 2. Compound Effects [Q61, Q62]

A compound card effect consists of multiple sub-operations (e.g., "Deal 3 damage, then heal your hero 2 HP"):
1. **Independent by Default [Q61]:** Sub-operations are executed sequentially. If sub-operation 1 partially fizzles (e.g., target leaves), sub-operation 2 proceeds normally unless explicitly flagged as conditional.
2. **Deferred Trigger Resolution [Q62]:** All sub-operations of the compound effect must finish committing their state changes before any triggered abilities generated by those operations begin processing in the FIFO queue.
3. **Intermittent Victory Checks [Q63]:** The engine tests for hero death and match conclusion immediately after each atomic sub-operation commits. If a hero dies during sub-operation 1, sub-operation 2 is canceled and the match terminates.

---

## 3. Simultaneous Damage Aggregation [Q64, Q288, Q289]

When an effect deals damage from multiple sources or hits multiple targets simultaneously:
1. **Target-Level Aggregation [Q64]:** Damage instances landing on the same target that share identical protection rules are combined into a single total before applying armor and shields.
2. **Protection Profile Grouping [Q288]:** Instances requiring distinct absorption logic (e.g., physical vs piercing) are partitioned by their effective protection profile.
3. **Canonical Shield Depletion & Simultaneous HP Commit [Q289]:**
   - Common consumable shield pools are depleted in canonical order across the groups.
   - All resulting HP deductions commit simultaneously.
   - No unit can die or trigger between the shield depletion and HP commit phases.
